An Echo Is Not a Witness: Evidence-Root Counting for Agent Audit Records

Abstract

An agent audit trail can contain many authentic records that ultimately repeat one observation. Signatures can establish the origin and integrity of records, but they do not establish that the records represent independent evidentiary support.¶

This document defines evidence-root counting as a separate audit semantic. Records derived from one declared evidence-provenance root contribute one unit of support, regardless of the number of copies, relays, summaries, translations, or re-signatures in the trail. The document describes the minimum provenance information needed to state such a count and the conditions under which the count remains not established. It does not define a wire format or claim to prove truth, causal independence, record completeness, or operational authority.¶

1. Introduction

Agent audit architectures correlate user intent, delegation, authorization, actions, and outcomes across administrative domains. Existing work distinguishes record integrity from questions such as whether a record was emitted, whether a decision preceded an effect, and whether an observed boundary can establish an external outcome. These distinctions are necessary, but they leave a separate counting problem.¶

Multiple audit records can repeat the same underlying observation. A relay can sign a received statement, a model can summarize it, or several services can repackage the same source event. Treating the resulting record count as an evidence count can manufacture apparent support without adding an observation.¶

The counting problem was raised during the AgentProto charter review in [COUNTING-DISCUSSION]. That discussion is a motivating record, not evidence that AgentProto has adopted the rule or that audit semantics fall within its current charter.¶

The rule in this document is narrow: when an audit report makes a multiplicity claim about support for a proposition, it counts declared evidence-provenance roots rather than record identifiers, signers, keys, services, agents, or messages. Five records derived from one evidence-provenance root still represent one evidence-provenance root. Adding a recorded descendant of an existing root does not change that count.¶

2. Scope and Terminology

This document concerns post-hoc interpretation of audit records. It does not define an agent communication protocol, authorization protocol, signature scheme, transparency service, or complete audit-record format.¶

Proposition
A question or assertion for which an audit report describes evidentiary support.¶
Record
An audit artifact that carries or references an assertion, observation, decision, action, or derived statement.¶
Derivation edge
A declared relation indicating that one record copied, transformed, summarized, translated, relayed, or otherwise derived its relevant assertion from another record or source.¶
Evidence-provenance root
A declared source node reached by following derivation edges for the proposition and error class under evaluation. This term is not a cryptographic trust anchor, certification root, or assertion that the source is true or independent.¶
Error class
The kind of shared failure or dependence relative to which sources are being distinguished. Independence is not a context-free property.¶

A report can establish that its declared graph contains two evidence-provenance roots. That fact alone does not establish that those roots are independent, truthful, complete, or correctly bounded. The strongest safe statement after an incomplete provenance investigation is that no declared dependence trace was found for the stated error class.¶

3. Evidence Multiplicity Is a Separate Verification Dimension

Audit systems need to keep the following questions separate. A successful check in one row does not imply success in another.¶

Table 1: Distinct verification dimensions
Dimension Question Success does not establish
Authenticity and integrity Did the identified signer produce these unchanged bytes? Truth, completeness, causation, or independent support
Recomputation Does the stated result follow from the available inputs and named procedure? Fresh external state or complete inputs
Freshness Was an external fact current at the claimed time? Causal use or evidence multiplicity
Completeness Did every attempt in a separately committed scope produce the required record? That present records are independent evidence
Precedence or effect Did a decision precede and govern an action, or did the claimed effect occur? More than one underlying observation
Evidence multiplicity How many declared evidence-provenance roots support the proposition? Truth, absolute independence, or authority to act

The architecture in [I-D.kuehlewind-audit-architecture] links intent, delegation, authorization, and execution through distributed records. The signed-decision-record work in [I-D.bradleyb-audit-decision-records] distinguishes correspondence from stronger ordering claims. Evidence-root counting composes with those efforts without replacing their checks.¶

4. Copy-Invariant Counting Rule

For a named proposition and declared error class, an audit report that states an evidence count follows this procedure:¶

  1. Identify the terminal records included in the report.¶

  2. Identify the derivation path from each terminal record to its declared evidence-provenance root or roots.¶

  3. State the basis used to qualify a root and to distinguish it from other roots for the declared error class.¶

  4. Count each distinct qualified root once, regardless of the number of descendant records.¶

  5. Report the multiplicity claim as not established when required derivation or distinction information is unavailable, cyclic, contradictory, or unsupported.¶

The copy-invariance requirement is:¶

Adding a same-side record with a declared derivation parent does not change the set of evidence-provenance roots, the root count, or the resulting root-count verdict.¶

A second signature can authenticate a second signer. It does not, by itself, create a second evidence-provenance root. The same restriction applies to a new agent, model, prompt, host, process, service, organization name, or public key when the relevant assertion remains derived from the same source observation.¶

5. Minimal Semantic Mapping

This document does not require a particular serialization. An audit format or profile can support the rule by carrying or referencing the following logical items:¶

Table 2: Logical items for evidence-root counting
Item Purpose
proposition_id Binds records to the same question before counts are compared.
assertion Names the side or value supported by the record.
derivation_parent_ids Preserves declared copy and transformation relationships.
root_basis_ref References the declared qualification, distinction basis, and error class used for the root.

The count is computed from roots reached under the cited rule, not from the number of records or unique identifiers. When a root basis is absent or does not support the claimed distinction, the report exposes the limitation instead of silently promoting each record to a root.¶

6. Completeness Requires an External Scope Commitment

No set of present records can, by itself, prove that an expected terminal record is missing. Completeness requires a separately committed finite set of expected attempts, or another auditable scope boundary against which omissions can be detected.¶

The public fixture at merge revision [MATRIX-FIXTURE] freezes three attempts and their terminal records. Deleting the terminal refusal leaves the remaining signatures and chain internally valid, while the separate attempt commitment makes the omission detectable. The fixture reports the missing record as a completeness violation. Without that external commitment, silence remains unverifiable.¶

Completeness and evidence multiplicity therefore produce separate verdicts. A trail can be complete and contain only one evidence-provenance root, or contain multiple declared roots while remaining incomplete.¶

7. Interoperability Exercise

A minimal evaluation publishes frozen inputs and expected outcomes for at least the following cases:¶

  1. One root with five direct copies; the root count remains one.¶

  2. Two separately qualified roots with any number of copies; the root count remains two.¶

  3. Two signatures over the same source observation; the root count remains one.¶

  4. Unknown, cyclic, or unsupported derivation; the multiplicity claim is not established.¶

  5. An expected attempt without its required terminal record; completeness is violated even when every present signature verifies.¶

The first four cases exercise evidence multiplicity. The fifth exercises completeness. Implementations do not collapse unavailable or unattempted checks into successful verification.¶

8. Limitations and Non-Claims

  • A declared root is not automatically true, authentic, qualified, or causally independent.¶

  • Different controllers can repeat one underlying observation, while one controller can operate genuinely separate measurement channels. Controller separation and evidence-provenance separation are different facts.¶

  • The procedure cannot detect dependence omitted from the declared provenance graph.¶

  • A root count is not a probability, confidence score, or authorization decision.¶

  • The symmetric counting rule is not directly applicable to universal or existential propositions whose opposing sides have different logical force.¶

  • External replay of supplied code demonstrates reproducibility of that implementation. It does not establish a separately developed implementation or an independent control domain.¶

The formal copy-invariance result underlying this mapping is described in [MINORITY-PROPHET]. Its guarantees are conditional on the declared provenance and root boundary.¶

9. Security Considerations

An attacker benefits when copies, aliases, re-signatures, or transformations are counted as new support. A format that omits derivation relationships permits this inflation while every individual record can remain authentic.¶

The opposite failure is also possible: falsely declaring distinct observations to share a root can suppress legitimate support. Implementations therefore expose the distinction basis and the relevant error class rather than treating either merging or splitting as universally conservative.¶

Provenance is itself an assertion. Forged, incomplete, selectively disclosed, or stale lineage can change the reported count. This document does not provide a mechanism for discovering undisclosed dependence. Reports preserve an unresolved state when the required provenance cannot be established.¶

Evidence assessment does not grant authority to execute an action. Authorization and enforcement remain the responsibility of the applicable protocol and deployment.¶

10. Privacy Considerations

Derivation and root-basis information can reveal relationships between people, organizations, services, or data sources. Implementations minimize disclosure and can carry digest references, selectively disclosed statements, or other privacy-preserving representations when a verifier can still evaluate the declared relationship.¶

Stable proposition, source, or lineage identifiers can enable correlation across contexts. Profiles should limit identifier scope, retention, and reuse to what the audit purpose requires.¶
